# 读懂一个陌生代码库

> 原文地址：[https://claucc.net/articles/cc-02-read-codebase](https://claucc.net/articles/cc-02-read-codebase)　·　更多教程见 [claucc.net](https://claucc.net)

接手一个没见过的项目，半小时内搞清楚它的结构、主流程和「坑」，再开始改。

## 一、先要地图，不要细节

第一句不要问某个函数，先要全局：

```
这是一个我刚接手的项目。请先不要改任何代码，帮我梳理：
1. 技术栈和模块划分（每个模块一句话说明职责）
2. 程序入口和一次典型请求的调用链
3. 构建、启动、测试的命令
4. 你觉得新人最容易踩的坑
```

它会自己 `ls`、读 `pom.xml` / `package.json`、找入口类，然后给你一张地图。**明确说「不要改代码」**，它就只读不写。

## 二、顺着一条真实链路往下追

地图有了，挑一个你马上要改的功能，让它把链路讲透：

```
「导出 Excel」这个功能，从前端按钮点击到文件下载，经过了哪些文件和方法？
按调用顺序列出来，每一步注明文件路径和行号。
```

要求「文件路径 + 行号」有两个好处：你可以直接点开核对；它也必须真的去读，而不是凭印象编。

## 三、让它找「为什么这样写」

老项目里很多奇怪的代码是有原因的。直接问：

```
SQL 都没有用 resultType="map"，而是专门建了 DTO 类，这是为什么？
有没有相关的注释、提交记录或文档说明？
```

它会去翻注释、`git log`、项目文档。很多「历史决定」就是这样找回来的。

## 四、对比两套实现

大项目里经常有新旧两套实现并存，最容易改错地方：

```
项目里好像有两套「智能问数」实现（模块 A 和模块 B），
它们分别从哪里进入、机制有什么不同？我要改「问数」该改哪一个？
```

搞清楚之后，**把结论写进 `CLAUDE.md`**，下次它（和你的同事）就不会再搞混。

## 五、大范围搜索交给子代理

要在几十个文件里找某种写法时，主对话会被大量搜索结果塞满。这时让它派子代理去查，只带回结论：

```
用一个子代理在整个项目里查：所有直接拼接 SQL 字符串的地方，
按风险高低列出文件和行号，不要贴代码全文。
```

子代理有自己独立的上下文，查完只把结论交回来，主对话保持干净（[第 04 篇](cc-04-subagents-skills.md)细讲）。

## 六、把理解沉淀下来

摸清楚之后，让它把关键结论整理进项目的 `CLAUDE.md`：

```
把我们刚才梳理出的模块职责、调用链要点、两套实现的区别，
整理成简洁的条目补充到 CLAUDE.md，不要写我们已经能从代码直接看出来的东西。
```

**只写代码里看不出来的东西**：设计原因、反常识的约定、容易混淆的地方。代码结构本身不用写，它每次都能自己看。

## 常见误区

| 误区 | 更好的做法 |
| --- | --- |
| 一上来问细节 | 先要地图，再顺链路深入 |
| 接受「应该是……」的回答 | 要求给出文件路径和行号 |
| 结论只留在对话里 | 写进 `CLAUDE.md`，下次直接复用 |
| 主对话里做大范围搜索 | 交给子代理，只要结论 |
