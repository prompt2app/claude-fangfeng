# 子代理与 Skills

> 原文地址：[https://claucc.net/articles/cc-04-subagents-skills](https://claucc.net/articles/cc-04-subagents-skills)　·　更多教程见 [claucc.net](https://claucc.net)

用子代理并行干活、做「不带偏见」的代码审查；把团队反复用的流程做成 Skill。

## 一、子代理是什么

子代理（subagent）是主会话派出去的「另一个 Claude」，有**独立的上下文**：

- 它读的文件、跑的搜索不会塞满主对话；
- 做完只把**结论**交回来；
- 多个子代理可以**同时跑**。

## 二、三个最值得用子代理的场景

### 1. 大范围搜索 / 调研

```
派一个子代理在整个仓库里查：哪些地方调用了导出工具类，
各自导出的是什么数据，只返回「文件:行号 + 一句话说明」。
```

主对话不用承受几百行搜索结果。

### 2. 独立代码审查（最推荐）

自己写的代码自己审，容易「顺着自己的思路」看不出问题。让子代理**只看代码、不看你的结论**：

```
派一个审查子代理。只给它改动的 diff 和新文件，不要告诉它我们的设计结论。
让它找：安全问题、并发 / 状态问题、会在运行时报错的地方。
每条给出文件行号、失败场景和修复建议。
```

实战中，这样一轮审查找出了 13 个问题，其中有几个很隐蔽：

- 组件把自己跳转到外站后，父页面还会继续给它发数据；
- 敏感词检查只查了前 2 万字，而代码上限是 10 万字；
- 某条路径改了数据列，但没有同步重写依赖列名的组件。

**拿到审查结果后要逐条核对**，确认属实再修，不要照单全收。

### 3. 并行独立任务

几件互不依赖的事可以一次派多个子代理同时做，比如同时调研三个参考实现、同时给三个模块补测试。

## 三、子代理的提示词怎么写

子代理只知道你写给它的内容，所以要像给同事派活一样写清楚：

- **目标**是什么；
- **去哪看**（文件、目录、文档）；
- **已经排除了什么**，避免重复劳动；
- **交回什么格式**（结论、行号、不超过多少字）。

## 四、Skills：把重复流程固化下来

Skill 是一份放在 `.claude/skills/<名字>/SKILL.md` 里的说明书，告诉 Claude「做某类事时按什么步骤、用什么脚本」。适合：

- 团队的开发规范（注释格式、修改日志、提交信息格式）；
- 固定流程（发版、发博客、生成报表）；
- 需要配套脚本的操作。

一个最小的 Skill：

```markdown
---
name: team-dev-rules
description: 团队开发规范。只在用户输入 /team-dev-rules 时使用。
---

# 团队开发规范

1. 修改已有核心逻辑时，在改动处加注释写明原因和日期。
2. 每次修改在模块的修改日志末尾追加一条，新增文件单独标出。
3. 提交信息格式：类型: 简要说明（如 fix: 修复登录返回 500）
4. 一个逻辑有两处调用就抽成公共方法。
5. 方法超过 50 行要拆分。
```

使用时输入 `/team-dev-rules`，它会按这份规范逐项检查当前改动。

### 写 Skill 的经验

- **description 写清楚什么时候用、什么时候不用**：这决定了它会不会被误触发。规范类的 Skill 建议设成「只在手动输入命令时使用」。
- **规则写原因**：和 `CLAUDE.md` 一样，带上「为什么」执行得更准。
- **能用脚本就用脚本**：确定性的步骤（建表、调接口）写成脚本放进 Skill 目录，比让 AI 每次现写可靠。

## 五、什么时候不用子代理

- 一两个命令就能查到的事，自己查更快；
- 需要你和它反复讨论的事，留在主对话；
- 子代理的结论要验证，**它说「没问题」不等于真没问题**。
