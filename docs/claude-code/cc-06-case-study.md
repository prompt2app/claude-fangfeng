# 实战复盘：一天做完「AI 报告支持自定义 HTML 3D 组件」

> 原文地址：[https://claucc.net/articles/cc-06-case-study](https://claucc.net/articles/cc-06-case-study)　·　更多教程见 [claucc.net](https://claucc.net)

一个真实需求从提出到上线的完整过程。重点看每个阶段人做了什么、Claude Code 做了什么。

## 需求

「AI 生成报告」功能参考我们另一款大屏产品，支持**自定义 HTML 组件**，用来做 3D 楼层、3D 地球这类内置图表做不了的高级组件。

技术背景：Java 后端 + Vue 前端，报告由 AI 规划、取数、生成。

## 阶段一：调研与方案（约 20 分钟）

**Claude Code 做的**：

- 读了模块的 `CLAUDE.md` 和报告的数据结构、四种风格（仪表盘 / 月报 / 大屏 / 打印）的渲染代码；
- 抓取参考大屏的官方文档，还从大屏前端打包文件里找到了原实现：iframe 沙箱 + 注入数据桥对象；
- 给出方案：分析项上加 `html` 字段，前端用沙箱 iframe 渲染，AI 按需生成代码，新增保存 / 生成两个接口。

**人做的**： 回答了两个选择题：3D 库允许走 CDN；AI 只在需求点名或内置图表做不到时才生成组件。

## 阶段二：开发（约 2 小时）

- **后端**：新增辅助类（提示词、HTML 清洗、样例数据组装），把 HTML 生成接进「生成报告」「对话修改」「新增分析项」三条链路，新增两个接口。
- **前端**：
  - 新增一个 HTML 渲染组件，负责沙箱 iframe 和数据桥；
  - 四种风格的渲染分支都接上；
  - 新增编辑弹窗：AI 生成 / 修改、代码编辑、实时预览；
  - 导出时向 iframe 要截图；
  - 大屏排版优先把 3D 组件当视觉中心。
- **示例**：内置几份示例报告。

中途有一次**方案调整**：原计划把 HTML 做成新的图表类型，调研发现图表类型在几十处有校验，于是改成「渲染覆盖层」，并主动说明了原因。

## 阶段三：用户反馈驱动的迭代

| 用户反馈 | 处理 |
| --- | --- |
| 「我手工添加，怎么看不到」 | 入口只放在卡片工具栏，漏了「添加组件」弹窗 → 补上第 5 种组件类型 |
| 「就做了一个吗」「做个高级点的」 | 示例在大屏里太小、太挤 → 重做两份高级示例，用显式布局让 3D 组件占大半屏 |
| 「参考原大屏的 3D 楼房」 | 从参考大屏的线上示例里取出原组件源码，发现原件是纯 CSS 3D，**直接移植**，不依赖外部库、内网可用 |
| 「样式有问题吧」+ 截图 | 定位到按钮用了 28px 的图标按钮样式、遮罩颜色借错了变量，逐一修复 |

**截图是最高效的反馈方式**：一张截图比一段描述准确得多。

## 阶段四：审查与测试

- 派一个**独立审查子代理**，只给代码不给结论，审出 13 个问题（安全、数据一致性、成本上限等），逐条核对后修了 12 个。
- 后端 47 项方法级测试（假 AI），前端 32 项浏览器测试，加示例截图回归。
- 测试过程中又发现并修了 2 个问题。

## 阶段五：规范与上线

- 按团队规范（一个 Skill）逐项检查：补 Javadoc 的作者和日期、把重复代码抽成公共方法、超过 50 行的方法拆分、修改日志合并成一条并标注新增文件。
- 更新模块 `CLAUDE.md`、待办清单、功能对比文档。
- 提交代码；再把新示例加进产品官网的示例列表：从线上真实页面截封面、改示例列表、本地起官网验证、提交。

## 复盘：哪些做法最值

1. **先方案后代码**：两个关键选择在开工前就定了，后面没有推倒重来。
2. **找到原实现再动手**：移植参考大屏的组件，比自己从零设计效果好得多、也快得多。
3. **独立审查**：自己写的代码，换一个「不知道设计思路」的视角，能看出很多问题。
4. **证据驱动**：每个阶段都有编译、测试或截图，用户看到的就是验证过的结果。
5. **规范固化成 Skill**：收尾时一条命令就能按团队规范把改动检查一遍。

## 哪些地方可以做得更好

- 第一版没考虑「添加组件」入口，靠用户发现才补上 → 方案阶段应该列出**所有用户入口**。
- 第一版示例太多、太小 → 示例应该**先想清楚展示什么**，少而精。
- 真实页面的验证依赖后端重启，部分验证只能离线完成 → 开发前就确认好验证环境。
