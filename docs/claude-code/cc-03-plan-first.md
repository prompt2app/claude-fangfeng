# 先出方案再写代码

> 原文地址：[https://claucc.net/articles/cc-03-plan-first](https://claucc.net/articles/cc-03-plan-first)　·　更多教程见 [claucc.net](https://claucc.net)

大一点的需求，先让它出方案、你拍板，再分步执行。这是减少返工最有效的一招。

## 一、为什么要先出方案

直接说「做一个 XX 功能」，它会立刻开始写。问题在于：

- 需求里有歧义的地方，它会**自己猜一个**；
- 涉及数据结构、接口设计的决定，一旦写进几十个文件，改起来很痛；
- 你看到代码时才发现方向不对，前面的时间全白费。

先花五分钟对齐方案，后面能省一小时。

## 二、Plan 模式：只看不改

按 `Shift+Tab` 切到 **Plan 模式**，或者直接在需求里说清楚：

```
需求：报表里支持自定义 HTML 组件，用来做 3D 效果。参考我们另一款大屏产品的实现。
先不要写代码。调研现有代码后，给我一个方案：
- 数据怎么存（要不要改表）
- 前端怎么渲染、安全怎么保证
- 需要新增哪些接口
- 有哪些需要我拍板的选择
```

Plan 模式下它只能读文件、搜索、查资料，不能改任何东西，最后给你一份方案。

## 三、好方案长什么样

一份能拍板的方案应该包含：

1. **现状结论**：它调研到了什么（关键文件、现有机制）。
2. **方案要点**：数据模型、接口、前后端分工。
3. **需要你决定的选项**：并给出推荐。比如：
   - 外部 3D 库走 CDN 还是本地内嵌？
   - AI 什么时候自动生成组件？
4. **风险和不做的事**：哪些点有安全风险、哪些暂不支持。

遇到真正需要你选的问题，它会用选择题的形式问你，你点一下就行。

## 四、拍板之后：分步执行

方案确认后，让它按步骤推进，并在关键节点汇报：

```
按方案执行。顺序：后端数据结构和接口 → 前端渲染组件 → 编辑弹窗 → 示例。
每完成一步先编译 / 自测，再进入下一步。
```

执行过程中如果发现方案有问题，好的做法是**它停下来说明，而不是自己改方向**。可以在 `CLAUDE.md` 里写明：

```markdown
## 交互规则
直接执行，不要反复确认。涉及数据库变更、接口设计、核心逻辑或架构调整时，先简要说明方案等我确认。
```

## 五、中途改需求怎么办

需求变了就直接说，它会在当前进度上调整。但要注意：

- **说清楚是「讨论」还是「改」**。「这样会不会有问题？」和「改成这样」是两回事，否则它可能把讨论当指令直接动手。
- 改动大时，先让它评估影响：「如果改成 XX，已经写好的哪些地方要跟着动？」

## 六、一个实际例子

需求：「报表支持自定义 HTML 组件」。

1. 它先调研：找到参考大屏的原实现（iframe 沙箱 + 数据桥），读了报表的数据结构和四种风格的渲染代码。
2. 给出方案，并提了两个需要拍板的问题：
   - 3D 库从哪加载？→ 选了「允许 CDN」；
   - AI 什么时候生成组件？→ 选了「点名或内置做不了时」。
3. 执行中，它发现「新增一种图表类型」会影响几十处校验逻辑，于是**调整为「在分析项上加 html 字段作为渲染覆盖层」**，并主动说明了这个调整和原因。

这种「方案里的调整有说明」正是先出方案带来的好处：你始终知道它在做什么、为什么这么做。
