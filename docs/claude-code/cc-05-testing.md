# 测试与自动化验证

> 原文地址：[https://claucc.net/articles/cc-05-testing](https://claucc.net/articles/cc-05-testing)　·　更多教程见 [claucc.net](https://claucc.net)

不接受「应该没问题」，让它用编译、测试、截图证明改动是对的。

## 一、验证的三个层次

| 层次 | 手段 | 能发现 |
| --- | --- | --- |
| 能不能跑 | 编译、语法检查 | 拼写错误、签名不对、语法错误 |
| 逻辑对不对 | 单元测试、方法级测试 | 边界条件、异常分支、业务规则 |
| 看起来对不对 | 浏览器截图、页面自动化 | 样式错位、空白、交互异常 |

让它在每一步改完都至少过第一层，关键逻辑过第二层，页面改动过第三层。

## 二、只编译改动的部分

大项目全量构建要几分钟。可以让它只编译改过的类：

```
不要整体构建。用 javac 只编译这次改动的几个类，classpath 用 mvn dependency:build-classpath 导出的那份。
```

前端 JS 至少跑一遍语法检查（如 `node --check`），模板可以用框架自带的编译器编译一遍，看有没有警告。

## 三、不启动整个服务也能测业务逻辑

很多逻辑依赖 AI、数据库、外部服务，不方便起整个应用。可以让它**直接实例化真实的类，把外部依赖换成假的**：

```
写一个测试：直接 new 出 XxxServiceImpl，用 Java 动态代理做一个假的 AI 服务，
按场景返回不同内容（正常 HTML、不是 HTML、含敏感词、超长），
用反射调用这些私有方法，验证每种情况的结果。
```

这样一次能跑几十个场景。实战中这类测试跑了 47 项，覆盖了「AI 失败时退回图表」「最多 3 个组件的上限」「改列后重写组件」等规则。

> 关键是测的是**真实代码**，只替换掉外部依赖，而不是另写一份模拟逻辑来测。

## 四、页面验证：无界面浏览器

前端改动用 Playwright 之类的无界面浏览器验证，它可以：

- 打开页面、等待加载、截图给你看；
- 在页面里执行脚本，检查组件状态、控制台报错；
- 模拟点击、输入，测交互流程。

几个实战技巧：

- **截图前要等够时间**，3D、图表、CDN 资源加载需要几秒；有时截图工具会拿到旧画面，可以用代码等待后再截。
- **登录页面拿不到时**，搭一个测试页，加载真实的 JS / CSS，把接口调用换成桩函数。
- **故意埋一个错误验证检查本身有效**：比如往模板里塞一个坏表达式，确认编译检查真的会报警。

## 五、测试也会写错

实战里遇到过两次「测试本身有问题」：

- 测试页的内联脚本里写了字面的 `</script>`，把脚本提前截断，导致整个测试超时；
- 一条断言还按旧行为写的（修复后 `0012` 应保留为文本，断言却期望转成数字 12）。

所以测试失败时，先判断是**代码错了还是测试错了**，不要为了让测试通过去改代码。

## 六、测试中发现的真问题

好的测试会顺带发现问题。实战中通过测试和截图发现并修复了：

- iframe 里的脚本在布局完成前执行，宽度为 0，画布一直空白 → 在桥接层统一补发 resize；
- 组件跳到别的页面后，`pagehide` 消息不一定送达 → 改为监听 iframe 的 `load` 次数；
- 效果描述只去掉了尖括号，`<b>热力</b>` 变成 `b热力/b` → 改成整段去掉标签。

## 本篇小结

每次改动后问自己（也要求它回答）：**用什么证据证明它是对的**？ 编译通过、测试通过、截图看过，三样都有才算完成。
